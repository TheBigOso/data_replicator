THE SPINE — A STREAM'S WHOLE LIFE
① New stream → Suspended · not activated → ② Activate — plan → apply + chained refresh → ③ Healthy · capturing ⇄ ④ Compare / Refresh ⇄ ⑤ Add / remove tables → Suspend → ⑥ Deactivate / retire
Any change to the definition — tables added, method changed, connection swapped — re-enters at plan. There is no path in the console that mutates a running stream without a diff first.

① NEW STREAM
Four steps, then inert
1 · Identity — name (identity rules, unique in the VF), description, accent.
2 · Source & target — from this VF's connections; the picker excludes classes the capability matrix says cannot take that role. Create one inline.
3 · Tables — browse or pattern-match the source catalog.
4 · Mode — continuous CDC · scheduled refresh · CDC + scheduled compare; apply style (replica / soft delete / history) and cadence.
Exit: the stream lands as Suspended · not activated and the console offers Activate replication →. The equivalent CLI is shown and exportable.
② ACTIVATE REPLICATION
Plan → review → apply
The hub diffs the definition against the real state of both connections and shows exactly what it will create. Nothing applies until approved. Re-activation is idempotent — unchanged components verify fast and report "no change".
Components
jobs · table registration · supplemental logging · state tables · capture position
Capture start
now · oldest open txn · rewind N min · recovery — target integrate seq · custom
Guard rails: recreating state tables drops recovery positions (flagged red) · recovery rewind blocked until the integrate sequence is fetched · partial table selection needs ≥1 table · rewind interval must be positive.
Emit time is independent of capture start — capture early to catch open transactions while emitting only what committed from a chosen moment. Chained refresh loads as-of the recorded position so the bulk load and CDC meet with no gap and no duplicates.
④a COMPARE — PROVE IT
Setup → running → report → repair
Scope — which tables (all by default), optional row restriction.
Method — tiered: row count → checksum → composed → row-by-row. Cheapest that can answer runs first.
Online truth — compare a live pair without stopping it; in-flight rows are held and re-checked, not reported as differences.
Repair — directed insert / delete / update, source→target or reverse, with a WHERE restriction.
Three honest outcomes: IDENTICAL · DIFFERENT (with counts) · INCONCLUSIVE when rows were in motion. Never a false green.
Closing the window does not stop the run — it continues in the background with a notice chip and a Jobs entry, and reopening restores it.
④b REFRESH — RELOAD IT
Bulk or row-wise, sliced when large
Method. Bulk (staged load, fastest) or row-wise (repair-style, restartable). Chosen per run, not fixed on the stream.
Target policy. Create missing · alter/recreate · keep structure · keep old rows · truncate and load — each stated in plain words before it runs.
Segmented load. Large tables split into segments loaded in parallel, with a segment map and per-segment progress; a failed segment retries alone.
As-of consistency. A refresh chained to activation reads at exactly the recorded capture position; a standalone refresh records its own.
Cancel is resumable — the run reports CANCELED with the segments already loaded retained.

⑤ ADD TABLES · DUPLICATE
Two modal sub-flows
Add tables — browse or pattern-match the source catalog, showing what is already registered so nothing is added twice. Newly added tables land unregistered and the stream is flagged as needing re-activation; the plan then covers registration, supplemental logging, and their initial load.
Duplicate — copies the definition only. The duplicate carries zero jobs, state, or history, shares the connection but keeps its own capture position and file log, and reports nothing moving until it is activated. The duplicate event names its source.
⑥ SUSPEND · DEACTIVATE · RETIRE
Three different amounts of undo
Suspend — jobs stop, positions held. Resume continues exactly where it stopped. No refresh needed.
Deactivate — removes runtime components. Retention-first defaults: state tables and registration are kept unless explicitly dropped; supplemental logging is never dropped automatically.
Retire — after the GC interval, zero files remain on the hub file store; the definition survives read-only with its full version history.
Destructive teardown is opt-in and confirmed by typing the stream name — never a default, never a single click.

RULES THIS SCREEN HOLDS TO
· Every definition change re-enters at plan — no silent mutation.
· Status is derived from job state, never asserted.
· Suspend holds positions; only teardown drops state.
· A table is not a stream — removing one leaves the rest running.
· A compare never reports a false green.
· A duplicate shares connections but never state or history.
· Every action shows its equivalent CLI and is ledgered.
