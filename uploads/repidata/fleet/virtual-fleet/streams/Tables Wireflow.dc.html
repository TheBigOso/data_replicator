Registration is a plan
Add tables registers only — capture starts at the next checkpoint; rows reach the target with the first refresh, never before
Two-step confirm
Checkboxes pick from the catalogue; a review step confirms the explicit list of what goes online — not whatever the boxes held
Catalogue-scoped
Read live from the source database; tables already registered in this stream are never listed — duplicates impossible by construction
Warnings travel
No-primary-key and logging flags show at pick and review, and land on the ledger event as the flagged list
Column plan per table
Renames, target-only columns, type overrides and keys are staged as plans — applied to the target on the next activation

OUTCOME · REGISTERED, THEN LOADED
Three-beat lifecycle
1 · Registered — rows land in the grid as Queued · refresh PENDING; a violet DEFINITION CHANGE hits the ledger: added list, source schema, flagged list
2 · Capturing — capture starts at the next checkpoint; changes buffer in the file log, nothing applies yet
3 · Loaded — the first refresh (chained off Activate replication) reads the snapshot; integrate skips captured changes ≤ snapshot — no gap, no double-apply
Toast repeats the contract: “capture starts at the next checkpoint; run a refresh to load the initial data.” See the Activation wireflow for the load itself.

SUB-FLOW · REMOVE A TABLE
Stop replication & remove
Confirm shows the full identity: stream · source object · target object · rows/day
Capture stops for the table; jobs drain at their checkpoints
Target data stays — exactly as last applied; nothing is dropped on the target
Logged as a red STOP event with a run-log artifact. Re-adding later = normal Add tables — it reappears in the catalogue.
→
INVARIANTS
Every table change is a ledger event — add, column edit, remove; the history outlives the table
Definition changes apply as plans on activation — the running stream is never mutated mid-flight
Registration ≠ data — rows only move on refresh, so an operator always knows when the target changed
