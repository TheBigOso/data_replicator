DIALOG · CAPTURE START (first activation only)
Where capture begins
◉ Now — current source position; chained refresh reads as-of the same position
○ Oldest open transaction, emit from now — “source has 2 open txns” + Fetch again
○ Rewind an interval — minutes 2, emit only changes committed from now
○ Recovery rewind to the target's integrate sequence — Fetch sequence…
○ Custom rewind… YYYY-MM-DD HH:MM · emit: after rewind time / from now / delayed until a source position
On an active stream this section reads “Held — already positioned; a rewind is its own guarded plan on the Stream Timeline.”
Sub-flow · Fetch sequence: reads the last-applied position from the target's state tables (hub-failover safe). Options: previous stream/location names for renamed setups + per-location previous-name fields; integrate-location checklist — multiple targets rewind to the oldest sequence. Result pins next to the radio: seq 0x3A81F2 · committed 22:41 · state table on databricks-lh.

DIALOG · INITIAL LOAD + START
Refresh chained after activation
☑ Load the target after activation — refresh the 61 selected tables
◉ Bulk — stage + atomic swap  ·  ○ Row-wise — repair only differences
Target tables: leave untouched ▾ / truncate and load
Reads as-of snapshot position S from activation; integrate keeps running and skips captured changes ≤ S per refreshed table — no gap, no double-apply, nothing suspended.

OUTCOME · ONE READING SURFACE
Activation's chained refresh, capture cycles, integrate cycles, latency, and errors all narrate into the same per-stream log — filterable, exportable, and watchable from any screen. Suspended and stopped streams explain themselves in-line (stream suspended — jobs drained at their checkpoints…) instead of going silent.
