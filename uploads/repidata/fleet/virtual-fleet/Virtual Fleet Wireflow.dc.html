BRANCH A · WIZARD · NEW STREAM
Define a replication unit — it starts inert
Four steps, each validated as typed. The wizard creates a definition, not a running stream; nothing moves until Activate replication is applied.
1 · Identity — name (identity rules, unique in the VF), description, environment accent.
2 · Source & target — pick from this VF's connections; the picker excludes classes the capability matrix says cannot serve that role. Create a connection inline without leaving the wizard.
3 · Tables — browse or pattern-match the source catalog; per-table overrides deferred to the Tables page.
4 · Mode — continuous CDC · scheduled refresh · CDC + scheduled compare; apply style (replica / soft delete / history) and cadence.
Exit: the stream lands in the table as Suspended · not activated, the tree gains a node, and the console offers Activate replication → as the obvious next step. The equivalent CLI is shown and exportable.
BRANCH B · ACTIVATE REPLICATION
Plan → review → apply, Terraform-style
The hub diffs the definition against the real state of every connection and shows exactly what it will create. Nothing is applied until you approve the plan. Re-activation is idempotent — unchanged components verify fast and report "no change".
Components (checklist)
Jobs · table registration (replace or add) · supplemental logging · state tables · capture position
Capture start
now · oldest open txn · rewind N minutes · recovery — target integrate sequence · custom position
Guard rails: recreating state tables drops recovery positions and is called out in red · recovery rewind is blocked until the integrate sequence is fetched · a partial table selection must select at least one table.
Chained refresh. Activation optionally runs the initial load as-of the recorded capture position, so CDC and the bulk load meet exactly with no gap and no duplicates.
Every apply is a record. Steps, timings, and warnings land in the VF log and the event ledger; the plan is archived as a versioned, attributed artifact.

BRANCH D · COMPARE ▾
Prove the target matches the source
A split button: Compare history reads, New compare writes. The window is a setup → running → results flow that survives being closed — a running compare keeps going in the background with a notice chip and a Jobs entry.
Scope — which stream, which tables (all by default), optional row restriction.
Method — tiered: row count → checksum → composed → row-by-row. Cheapest method that can answer the question runs first.
Online truth — compare a live pair without stopping it; in-flight rows are held and re-checked rather than reported as differences.
Report → repair — per-table missing/extra/updated counts, then an optional directed repair (insert / delete / update, source→target or reverse).
Three honest outcomes: IDENTICAL · DIFFERENT (with counts) · INCONCLUSIVE when rows were in motion — never a false green.
BRANCH E · VF TIMELINE
What is running right now, and what checked out
The operational view the fleet timeline links into. Three bands, one per class of thing happening inside the VF.
CONCERNS — open conditions: stream errors, latency over SLA, agent CPU/memory/IO above threshold. Each chip deep-links to the offending object.
JOBS — capture, apply, refresh, and compare jobs with live state (RUNNING / WAITING / RETRY / DONE / FAILED) and suspend/resume where granted.
CHECKS — system cards for the hub, repo database, and every source/target agent: health, CPU, memory, IO, version.
Ordering is deterministic and thresholds are evaluated against wobble-free values, so nothing reshuffles or flickers on a live tick. Counts here are exactly the counts the fleet timeline shows for this VF one level up.
BRANCH F · ⚙ VF ADMIN
The bottom tier of the three-level admin model
Same admin screen as Global and Fleet admin, scoped to one VF: "VF Admins can edit this virtual fleet's admins, manage/update this virtual fleet, and edit any connection, table, alert, job, and event — within it."
Virtual fleet Users Permissions Alert rules
Virtual fleet
Description, scheduler cycle, freeze / unfreeze, snapshot, export definition, delete (typed confirmation), stats retention. Freeze suspends the scheduler and holds capture positions — it never drops state.
Users
Accounts whose grants land in this VF, with service accounts flagged. Creating an account is Fleet or Global Admin's job — here you attach existing ones.
Permissions
Grants scoped to this VF only: HubOwner / ReadExec / ReadOnly. Cannot grant fleet or repository scope — a VF admin can never widen their own reach.
Alert rules
Rules watching this VF's logs, one notification channel each, with the retry/backoff curve and delivery-failure history.
Gate: ⚙ renders for HubOwner on this VF, or anyone with an inherited fleet/repository grant. Deleting the VF is the only action that also requires the fleet-level role.
THE LIFECYCLE THIS PAGE OWNS
New stream → Suspended · not activated → Activate — plan → Apply + chained refresh → Healthy · capturing → Compare — prove it → Deactivate / retire
Each transition writes to the VF log and the event ledger with an attributed, versioned artifact. Re-activation after a definition change re-enters at plan, never at create — the console has no second path that skips the diff.
RULES THIS PAGE HOLDS TO
· Nothing replicates until a plan is applied — creation is always inert.
· A compare never reports a false green; in-motion rows are INCONCLUSIVE.
· Freeze holds positions; only an explicit teardown drops state.
· A VF admin cannot widen their own scope.
· Suspended is a deliberate state and never enters triage.
· Every action shows its equivalent CLI and is exportable.
