WHAT IS AND IS NOT AN EVENT
The line that keeps the ledger useful
IS AN EVENT
Every user action that changes something — activate, suspend, disable, compare, refresh, definition change, permission grant, enrollment, export, sign-in. Plus scheduler-initiated work that a user could have initiated.
IS NOT AN EVENT
Read-only activity and automated job cycles. Those live in the job logs. A capture cycling 18,422 times is not 18,422 audit records — it is one running job.
Get this line wrong in either direction and the ledger dies: too permissive and it becomes an unsearchable firehose that no auditor will read; too strict and a change happened that nobody can attribute. The test is "could someone be asked to justify this?"

Events is the closed set; Jobs is the open set — the same record in two tenses. A job that finishes does not write an event, it becomes one, keeping its id. That is why an in-flight compare or refresh appears here as CURRENT rather than as a second, separate row.
THE FIVE FIELDS EVERY EVENT CARRIES
Identity — a sortable, microsecond-precision id that doubles as the timestamp: 2026-08-01T23:48:35.709101Z
Type — SUSPEND · REFRESH · COMPARE · ACTIVATE · DEFINITION CHANGE · GRANT · ENROLL · EXPORT · SIGNIN · STOP
State — CURRENT (open) · WAITING (scheduled) · DONE · FAILED · CANCELED
Scope — fleet / virtual fleet / stream / connection. Every event is placed somewhere in the hierarchy
Attribution — a named person or scheduler. Never blank, never "system" as a dodge
Mirrors the industry HVR_EVENT shape so migrating operators recognize it — but the vocabulary, the parameter block, and the artifact link are ours.

LAYER 1 · NARROWING
Six filters that compose
All streams ▾ All connections ▾ Type: all ▾ State: all ▾ Started: any time ▾ Search events…
All 142 matching events Columns ▾
All six AND together, and the matching count is always visible — so a narrowed view can never be mistaken for an empty ledger. That distinction is the whole reason the count is a permanent fixture rather than a footer.
Scope filters name real objects (streams, connections in this VF), not free text — a typo cannot silently return nothing.
Event ID is the default sort, descending, with the ▼ indicator visible on load. Because the id is the timestamp, sorting by id and sorting by time are the same operation — there is no way for them to disagree.
Column chooser persists per user; filters are session-only. Looking is transient; setup is a preference.

LAYER 3 · THE EVIDENCE
Every event points at its artifact
ACTIVATE → the applied plan diff
COMPARE → the compare report, per table
REFRESH → the run log with segment detail
DEFINITION CHANGE → the versioned before/after
EXPORT / ENROLL → the export manifest, the token record
View log opens the job log positioned at that event's timestamp — not the top of the file. An audit trail that makes you scroll for the moment is not a trail.
UPGRADE ① · FILTER BY ARTIFACT
Auditors search by artifact, not by time
"Show me every compare report from Q2" is the actual question. Today it can only be reached by combining Type and a date range and hoping. A seventh filter makes it direct.
any artifact plan diff compare report run log export manifest token record has no artifact
"has no artifact" earns its place too — it is how you find the events that changed something but left no evidence, which is exactly what an audit should surface.
UPGRADE ② · RETENTION, STATED
A ledger with no retention policy is not an audit ledger
retained36 months (regulated default) oldest held2024-02-11 · 29 months at the edgearchived to the hub file store, not deleted artifactsretained with their event, same window set byGlobal Admin · applies fleet-wide
Stated on the screen, not buried in settings — an auditor reading a 14-month-old event needs to know whether the 20-month-old one still exists. And what happens at the edge matters as much as the number: archived and retrievable is a different promise from deleted.

UPGRADE ④ · DIFF VIEW
Show the change, not a sentence about it

EVENTS IN THE FOUR-LEVEL HIERARCHY
Stream
The "Recent events" strip — a preview of the ledger, not a second source. Same ids, same attribution.
Virtual fleet (this)
The full ledger for the VF, with all filters and the expandable record.
Fleet
Events appear as markers in the fleet log and as condition chips on VF cards.
Global
Only triage-worthy events surface, in the needs-triage strip and its 90-day history.
One ledger, four viewports. No level keeps its own copy, so a count at any level is a filtered read of the same records — which is what makes "the number here matches the number there" true by construction rather than by discipline.
RULES THIS SCREEN HOLDS TO
· Every change is an event; no read or job cycle is.
· Attribution is never blank — a person or the scheduler.
· Events are immutable; a correction is a new event.
· The id is the timestamp, so sort order can never disagree.
· The matching count is always visible — filtered ≠ empty.
· An open event states what would close it.
· View log opens at the event's moment, not the top of the file.
· Exporting the ledger is itself a recorded event.
