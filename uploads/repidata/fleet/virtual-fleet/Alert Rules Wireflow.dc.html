SUB-FLOW · The alert manager — a scheduler job on a configurable cycle (5–60 min, default 10, set inline on Fleet Alerts), executing every enabled cycle-scheduled rule; own-interval and digest rules run as their own tasks
CYCLE START
13:30:26 Checking alert rules.
13:30:27 Checked 2 rules for 6 streams in 1 second.
Visible in the Alert manager log panel on Fleet Alerts. Disabled rules are skipped.
→
SCAN · SCOPED
Hub logs are read once per cycle; each rule filters to its streams / connections, severity classes, and ignore pattern. Inactivity checks compare the quiet window against the configured minutes.
→
MATCH → NOTIFY
One notification per rule per cycle (or per event, if split). Repeat interval silences repeats of the same issue; blackout suppresses the send, not the scan; message limit caps quoted lines — the rest are counted.
→
RECORDED
• Last check updates on the rule row
• an event per notification (when enabled) lands on the Events ledger
• the notification links the alert it fired for — alert → run → event → artifact
Gate: a rule not executed within its grace window — 2 h on the cycle, 2× its own interval, 26 h for a digest — shows ⚠ check overdue on its row (unless disabled). A rule idle past 5 hours scans only the most recent log on its next run — archived logs are skipped to keep the catch-up cheap.
BRANCH · schedule & recurrence — three ways a rule runs
◉ EVERY MANAGER CYCLE · default
Rides the shared wake-up — no config of its own. The cycle itself is set inline in the rules header:
the alert manager scans hub logs every 10 minutes ▾ — 5 / 10 / 15 / 30 / 60 min; persisted, DEFINITION CHANGE on the ledger
○ ON ITS OWN INTERVAL
A separate scheduler task — every 30 min / 1 h / 6 h / 12 h, independent of the manager cycle. Matches found between runs wait for the next run.
Row reads every 6 hours under Last check; the manager log notes “N rules run on their own schedule”.
○ DAILY DIGEST
One bundled notification at a set time — 07:00 — on chosen days: Mo Tu We Th Fr Sa Su. Nothing sends in between; repeat interval doesn't apply.
Default rule nightly_digest ships this way — weekday mornings, whole fleet.
Log ◎ nightly_digest.out daily digest 07:00 · whole virtual fleet
07:00:00  alert(nightly_digest): digest window closed — scanning hub logs since the previous digest — whole virtual fleet.
07:00:01  bundled 3 issues: mssql-hr capture stopped · db2-mfg latency 96s · DDL pending on ERP.AP_INVOICES
07:00:02  digest sent via EMAIL to dataops@corp.example (6 lines quoted).
07:00:02  event recorded on the Events ledger.
Branch: changing the manager cycle never touches own-interval or digest rules — they are their own tasks. “Perform alert check now” works on any schedule and resets Last check. A digest with no digest days can't be saved.
BRANCH · silence & snooze — suppress the send, never the scan
PER-RULE SNOOZE · ⋮ menu
Snooze 30m 1h 4h 24h ∞ · custom [hours] — snoozed rules swap to a single Resume notifications item
The row shows snoozed · 42m under Last check. The rule keeps executing on its schedule and keeps logging; only the send is held. Auto-resumes when the timer expires; persisted with the rule.
FLEET-WIDE SILENCE · rules header
Silence fleet ▾ — 30 minutes / 1 hour / 4 hours / until tomorrow 07:00 / mute until turned back on / custom [hours] · while active the button reads Silenced · 42m (or Silenced · ∞)
🔸 Banner above the rules table: Fleet-wide silence until 14:32 · 42m left — every rule keeps scanning and logging; nothing notifies. [Resume notifications]
Covers every rule regardless of schedule. Persisted — a reload doesn't un-silence; an infinite mute holds until resumed manually. Ledger records set and lift as DEFINITION CHANGE.
13:40:12  alert(fleet_errors): scanning hub logs — whole virtual fleet.
13:40:13  matched 1 issue: mssql-hr capture stopped
13:40:13  notifications suppressed — rule snoozed until 14:32; scans and logging continue.
Gate: snooze ≠ disable — a disabled rule stops executing; a snoozed one only stops sending. Send test notification still works while snoozed (an explicit test is never held). Alerts themselves stay on the page — silence mutes streams, not the console.
BRANCH · hub health × alert thresholds — rules watch the hub, not just the streams
CONDITIONS · in the rule dialog
Relay backlog over N MB — relay files piling faster than apply drains · Agents connected below N — lost hub connections · Frozen-hub watch — repository and GC paused. Effective thresholds are the tightest across enabled rules; each remembers which rule set it.
CARDS · hub health, threshold-aware
● stream-east · Relay backlog 352 MB · Agents 6 · repo ok
⚠ backlog over 256 MB (fleet_errors)
Breached metrics color and name their watcher; the card dot escalates (amber / red). Unwatched fleets read “no alert thresholds set” — the gap is visible, not silent.
ALERTS · same list as stream alerts
A breach is a live alert row on Fleet Alerts — WARNING backlog/frozen, CRITICAL agents under minimum. Acknowledgeable like any alert; counted in badges; matched by unscoped rules — so digests, previews and rule logs carry hub health too.
Branch: hub alerts carry no run — thresholds are evaluated against live hub status each cycle; the rule log states each check: hub health: relay backlog 352 MB vs 256 MB threshold — OVER. Stream-scoped rules never match hub alerts — hub health is fleet-level by definition.
BRANCH · escalation tiers — unacknowledged alerts climb the ladder
DIALOG · ESCALATION — tier 1 is the notification itself
2 Team leads · dl-dataops-leads@corp.example · if unacknowledged after 30 min ✕
3 Executives · exec-oncall@corp.example · if unacknowledged after 60 min ✕
+ Add escalation tier
No tier limit — 3, 4, 5 groups, each with its own group name, destination, and wait. Waits chain: tier 3 fires its wait after tier 2 fired. Every tier needs a destination to save.
RUNTIME · the chain in the rule log
13:20:18 notification sent via EMAIL to dataops@… — tier 1.
13:50:18 no acknowledgement after 30m — escalated to tier 2 (Team leads) via EMAIL to dl-dataops-leads@….
14:50:18 no acknowledgement after 60m — escalated to tier 3 (Executives) via EMAIL to exec-oncall@….
14:54:18 alert acknowledged by rn.reeves — escalation chain stopped.
Acknowledge is the off switch — acknowledging the alert (or turning the rule off) stops the climb wherever it is. The rules row reads · 3 tiers; the saved event carries the whole ladder.
Gate: a tier without a destination can't be saved. Snooze/silence hold tier-1 sends — and a chain that never started never escalates; blackout defers the send, and the escalation clock starts when tier 1 actually fires.
BRANCH · test & preview — see the payload, prove the stream
ENTRY · two doors, one modal
⋮ · Test delivery & preview on a saved rule — or Preview & test in the dialog footer, working on the unsaved form so the config is proven before Create rule is ever clicked.
The preview renders from the rule's current settings against the live alerts it matches — header fields (From/To/Subject, webhook + stream, topic ARN, trap destination) plus the message body, capped by the message limit. Missing required fields show in red.
DELIVERY TEST · simulated trace
connecting to smtp.corp.example:587 …
STARTTLS established — server certificate matches the pinned cert.
authenticated as svc-replicator.
test message accepted for 1 recipient.
Steps stream in per stream — SMTP connect/TLS/auth, Slack POST + HTTP 200, SNS publish + message id, SNMP trap (UDP, no ack). Verdict pill: TEST DELIVERED or TEST FAILED — a missing recipient / webhook / ARN fails the way the real stream would.
Gate: tests bypass snooze, fleet silence and blackout — an explicit test always sends. The preview never mutates the rule; closing the modal returns to wherever it was opened (dialog stays open behind it).
BRANCH · managing a rule (row actions + ⋮ menu)
Disable / Enable
Disabled rules stop executing until re-enabled — the row dims and Last check reads disabled. Test / check / clear are only offered while enabled.
Test delivery & preview
Opens the Test & preview modal — the rendered payload against live alerts, plus a simulated delivery trace with a DELIVERED / FAILED verdict. Also reachable unsaved, from the dialog's Preview & test.
Perform alert check now
Executes the rule immediately, outside the cycle; Last check resets.
Clear outstanding errors
Pending errors are disregarded — only new errors notify on the next run.
Duplicate rule
Opens the dialog prefilled as name_copy — rename before saving.
View rule log
Opens <name>.out in the Log drawer — see the log box below.
Delete rule
Removes the .conf; recorded in the ledger. The alert history it produced stays on Events.

alert-manager.out
The scheduler job's own log — one Checking / Checked pair per cycle (configurable, default 10 min) across every enabled cycle-scheduled rule. Opened from the Alert manager log button on Fleet Alerts.
<rule>.out
One rule's execution history: each cycle logs the scoped scan, then matched issues → notification sent (destination + quoted-line count) → event recorded — or “0 errors, 0 warnings matched”, or “silenced by repeat interval”. Opened from ⋮ · View rule log.
The viewer
Docked in the page by default — a panel right under the rules table, part of the Fleet Alerts layout. ⇱ Overlay floats it over any screen; ⇲ Dock in page puts it back. The choice persists. One log at a time — opening another replaces the tab.
Follow / Pause
Follow tails the file live; Pause freezes the lines on screen while the file keeps growing — resume to catch up.
Download · Copy path
Download grabs the whole file, not just the visible tail. Copy path yields $HUB_CONFIG/hubs/<vf>/alerts/<file> for CLI work.
What the log proves
Every notification names its trigger — alert → run → event → artifact — so “did it fire, and why not” is answered by the file, not by memory. Disabled rules log their suspension; overdue rules log the archived-log skip.
BRANCH · what each notification type needs
Email
Recipients (comma-separated) + SMTP server · optional auth (user/password), STARTTLS (pinned cert), from address, port — 587 with TLS, else 25.
Slack
Incoming webhook URL · optional explicit #channel or @user override. Message limit capped at 40.
SNS
Topic ARN + IAM access key ID / secret access key.
SNMP
Hostname (default localhost) · trap port (162) · community · version V1/V2C · heartbeats — a summary trap even when there is nothing to report.
All types
Message limit · repeat interval · split events · event-per-notification. Secrets are stored on the hub, never echoed back into the dialog.
