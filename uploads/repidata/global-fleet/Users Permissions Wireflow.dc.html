GATE · STRICTLY DOWNWARD
Same tabs, three scopes
Global (SuperAdmin/SysAdmin): every account, every grant.
Fleet: accounts + hub-level grants within its fleet — never repository grants.
VF: current-VF grants only.

Out-of-scope rows still render for context but lock: 🔒 read-only replaces Revoke.
No self-lockout: a SuperAdmin edits anything except revoking their own SuperAdmin grant.

Columns: User · Fleet · Virtual fleet · Permission (pill — hover reveals the concrete grant list) · Auth · Status · Last active · Granted. Only SysAdmin (any hub) and HubOwner (their hubs) manage access. All Users is a grantable principal — its rows drive new-user inheritance.

DIALOG · ADD ACCESS
Principal → scope → tier
1. Pick the user (or All Users)
2. Pick the scope: repository, a fleet, or a VF
3. Pick one tier (radio) — ReadWrite opens sub-options when selected
4. Grant → row appears, ledger event written

PERMISSION TIERS
REPOSITORY-LEVEL
SuperAdmin — everything, everywhere; implies all others; grantable only by a SuperAdmin
SysAdmin — full system incl. all hubs + user management
HubCreation — create hubs (implies HubOwner on them)
ReadStatistics — fleet-wide stats, sizing, sync reports
FleetViewer — Global Fleet console, read-only
HUB-LEVEL (one scope)
HubOwner — full control incl. access + properties
ReadWrite — edit objects (+ sub-options)
ReadExecRefresh — refresh, compare, jobs, view
ReadExec — compare, jobs, view
ReadOnly — view only
→
EVERY CHANGE IS A LEDGER EVENT
• create user / disable / re-enable / credential reset
• grant added → new Permissions row, visible at every level that can see the scope
• revoke → row gone; the account is untouched
• All Users grant → every future user inherits it on creation
• effects are immediate: tree visibility, Switch buttons, admin entries, and the FleetViewer gate all re-evaluate from grants
Then: the user lands on the highest scope their grants reach at next sign-in — grants, not roles on the account, decide everything they see.
